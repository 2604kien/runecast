## Proposed first-release scope

Existing direction stays: portrait mobile play, a 4 by 4 circuit, one centered enemy without a visible player character, cartoon fantasy art, branching tower progression, and runs targeting 15–25 minutes. Preserve compact rune choices, the substantial enemy arena, bottom Menu/Map/Guide/Sound navigation, and no separate forecast bar above Cast.

The [v1 design specification](v1-design-spec.md) and [content roster](content-roster.md) define the following **proposed working defaults**, not owner-approved quantities. RC-002 makes the budget concrete without adding content families. RC-006's owner decisions and RC-007's accepted contract now govern production content; the historical experiments remain separate.

| Area | Small first-release target |
| --- | --- |
| Playable setup | One spellcaster/loadout and one tower theme; tutorial plus a repeatable complete run. |
| Route | Nine visited rooms by default, within an 8–10-room budget including the guardian; alternate branches include normal combat, elite combat, shop, recovery and events. Adjust within that budget to measured 15–25 minute run time. |
| Enemies | Five distinct designs: three normal, one elite, one guardian. Shadeling is proposed as the first normal enemy because its existing simple attack cycle supports teaching; its reference appearance does not make it the guardian. |
| Boards | Four stable board identities with distinct teaching/content roles and authored construction examples. All share the accepted random-endpoint generation policy; their IDs do not create different mechanical difficulty. |
| Runes and techniques | Twelve permanent card definitions in total, including the four current permanent definitions; generated Free Spark is additional and not a collection card. |
| Progression content | Six relics, four events, eight single-rank rune upgrades, one run currency, and the bounded recovery/shop services in the roster. No meta-progression economy. |
| Presentation | One layered crypt environment with inexpensive room/lighting variants; one separate Home tower illustration and in-game Rune Cast logo; five character packs; reusable UI/icon kit and parchment map art; core effects and sound cues; two looping music tracks plus ambience. |
| Product | Offline, single-player, English first release with local saves. Keep UI text maintainable for later translation. |

Multiple simultaneous enemies, online accounts/cloud saves, multiplayer, ads/IAP, daily challenges, endless modes, extra characters/biomes, and translation production are deferred unless scope changes explicitly add them. No backend is needed for the proposed release.

The four [approved screen references](visual-reference.md) control visual direction; their functional states are proposed in the [specification](v1-design-spec.md). Home distinguishes no save, a valid save and an invalid save, and confirms replacement of an active run. Menu Quit returns to Home, preserving the between-room checkpoint or replaying an interrupted battle from its pre-battle checkpoint; it does not abandon the run. Menu Shop opens only the current unresolved shop room and is otherwise disabled with an inspectable explanation. Home and Menu share Options. Map supports inspection of current, available, locked and visited nodes, with turquoise current, gold next choices and completed checks, without a legend strip. Combat keeps the centered enemy, 4 by 4 board and compact hand while providing touch inspection, invalid-circuit feedback and an explicit pass action.

External availability is tracked in the specification: Android devices (RC-021), Mac/Xcode and iOS devices/development signing (RC-022), distribution accounts and production identity/identifiers (RC-052), and human participants (RC-006/RC-023/RC-045/RC-055). Availability is unknown unless supported by recorded evidence; these prerequisites do not block the completed RC-002 documentation. OS/device minimums are selected and recorded through RC-021/RC-022, then verified by RC-049.

No calendar estimates are assigned: availability, asset iteration, device access, and playtest results are not known. Dependencies and milestone evidence determine the order.

5. A task is complete only when its stated acceptance evidence exists. Record partial work and external blockers rather than checking it off. An asset file, desktop screenshot, or export preset alone does not prove in-game/device acceptance.

### Asset delivery checklist for every production task

- Supply editable or high-resolution source masters separately from runtime files; record how generated assets were made/refined and retain relevant prompts.
- Use each asset's agreed ID, path, dimensions, origin/anchor, animation states and import settings. Do not assume a full-screen reference is production-ready.
- Provide a contact sheet, isolated preview or listening sample and an in-game scale preview as appropriate. Character alpha, SVG import and frame scaling must be checked.
- Keep text and numerical state in Godot controls. Distinguish gameplay states through shape/symbol as well as colour.
- Record provenance, licence/attribution and readiness. Use states such as `planned`, `source-ready`, `runtime-ready`, `integrated`, and `device-verified` so production and integration are not confused.
